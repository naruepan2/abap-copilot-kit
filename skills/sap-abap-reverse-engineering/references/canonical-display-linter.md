# Canonical Display Linter
Blocking validation. Preserve the exact complete canonical object name returned by SAP discovery or verified from source/metadata, character-for-character. Carry that name unchanged from discovery into every technical-specification mention. Do not shorten, rewrite, normalize, reconstruct, or substitute a display alias. Never abbreviate by listing a base name once and then using suffix-only references such as `_0`, `_1`, or `_TMP`, nor by using shorthand labels such as `_2`, `_Tmp`, `Tmp`, `ZI passthrough`, `ContractGeneral`, or `GLAccount_0`.

For example, if the verified objects are `ZI_FIXTURE_CPLT`, `ZI_FIXTURE_CPLT_0`, and `ZI_FIXTURE_CPLT_1`, write each full name every time it is referenced; do not write the base name once and later use `_0` or `_1` as standalone labels. The supplied dependency export spells the temporary variant `ZI_FIXTURE_ROOT_Tmp`; preserve that exact case and full name, never refer to it as `_Tmp` or `_TMP` alone. A suffix is allowed only as part of a verified complete canonical name. Do not infer that a suffix is a real object: verify its canonical name. If a label cannot be resolved, mark it unresolved rather than inventing or shortening it.

Apply this rule to headings, prose, tables, findings, paths, lineage, evidence registers, Mermaid node labels, and completion reports. Short internal Mermaid IDs are allowed only as graph syntax identifiers when the full canonical name remains visible in the node label (for example, `N1[\"ZI_FIXTURE_CPLT_0\"]`). Preserve aliases only when quoting literal source; explain the canonical object separately. Run this as a blocking check and fix every violation before final acceptance.
